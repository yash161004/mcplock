# Harness findings

Per [PHASE4_NOTES.md](PHASE4_NOTES.md): findings against `fixtura` /
`openeval-core` are first-class, reported rather than worked around, and kept
separate from anything about mcplock or the filesystem server. Both are the
author's own projects, so no disclosure window applies.

## H-001 — `fixtura` installs no `fixtura` module, and claims five generic top-level names

**Severity: high.** `fixtura` 1.0.7, reproduced in a clean venv on Python 3.14.2.

`pip install fixtura` succeeds and `pip show fixtura` reports it installed, but:

```python
>>> import fixtura
ModuleNotFoundError: No module named 'fixtura'
```

`top_level.txt` declares:

```
cli
recorder
replay
security
tools
```

These are installed as **top-level packages in site-packages**. After installing
fixtura, in that environment:

```
import cli        -> .venv/Lib/site-packages/cli/__init__.py
import recorder   -> .venv/Lib/site-packages/recorder/__init__.py
import replay     -> .venv/Lib/site-packages/replay/__init__.py
import security   -> .venv/Lib/site-packages/security/__init__.py
import tools      -> .venv/Lib/site-packages/tools/__init__.py
```

Two problems, the second worse than the first:

1. **The documented import does not exist.** Anything following the README's
   `import fixtura` fails immediately.
2. **It squats five of the most collision-prone names in Python.** Any other
   installed package — or the user's own `tools.py` / `cli.py` — either shadows
   fixtura or is shadowed by it, depending on `sys.path` order. This can break
   unrelated code in any environment that happens to include fixtura, with a
   failure mode that gives no hint fixtura is involved.

**Not worked around.** This experiment imports `from recorder.recorder import
ExecutionRecorder` — the name that actually exists — with a comment pointing
here. Using the real name is not a workaround; suppressing the finding would be.

**Suggested fix:** move everything under a `fixtura/` package
(`fixtura.recorder`, `fixtura.tools`, …), keep `import fixtura` working, and
release as a major version, since it is a breaking import change.

**Note this is orthogonal to the earlier `openeval-core>=0.2.1` pin fix.** That
one made `openeval.adapters.fixtura` importable. This one means the `fixtura`
distribution itself was never importable under its own name. The adapter's lazy
imports are why the pin fix appeared to work — the adapter reads `.trace` files
from disk and never imports fixtura, so nothing surfaced the problem.

## H-002 — `EvalTestCase.expected_tool_calls` is untyped, and a wrong key raises a bare `KeyError`

**Severity: low — developer experience, not correctness.** `openeval-core` 0.2.1.

`expected_tool_calls: list[dict]` declares no shape. The metrics require the key
`"tool"`:

```python
expected_tools = [call["tool"] for call in test_case.expected_tool_calls]   # metrics.py:27
tool_names = [c["tool"] for c in expected_tool_calls]                       # metrics.py:60
```

But `TraceStep` names the same concept **`tool_name`**. Passing
`{"tool_name": "read_media_file"}` — the obvious guess given the neighbouring
model — produces:

```
KeyError: 'tool'
```

with no indication of which key was expected or which entry was wrong.

**To be clear, this was my error, not a defect in the scorer** — the metric
behaves correctly once given the documented-by-source key, and my code is fixed
rather than the library. The finding is that the API makes the error easy to
reach and hostile to diagnose.

**Suggested fix:** either a typed `ExpectedToolCall` model, or
`call.get("tool")` with a raised `ValueError` naming the expected key and the
offending entry. Accepting `tool_name` as an alias would remove the asymmetry
with `TraceStep` entirely.
